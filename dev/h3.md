# Goal
Add first-class HTTP/3 support to Harmony so that a network can terminate HTTP/3/QUIC directly (not just behind another proxy), using a pure-Rust stack (no BoringSSL), while reusing the existing pipeline, service, and envelope infrastructure as much as possible.
# Current state (summary)
* `ProtocolAdapter` trait in `src/adapters/mod.rs` abstracts protocol listeners (currently HTTP over TCP via Axum, DIMSE via DimseAdapter).
* `AdapterRegistry` (`src/adapters/registry.rs`) decides which protocols to start for each network based on pipelines/endpoints -> services -> `required_protocol()`. It currently instantiates `HttpAdapter` for `Protocol::Http` and `DimseAdapter` for `Protocol::Dimse`.
* `NetworkConfig` (`src/models/network/config.rs`) exposes:
    * `enable_wireguard: bool`
    * `interface: String`
    * `tcp_config: TcpConfig` (aliased from `[network.name.http]`), used by all TCP-based adapters.
* HTTP adapter (`src/adapters/http/mod.rs`):
    * Uses Axum + Hyper, listening on a `TcpListener` and serving a router built in `src/adapters/http/router.rs`.
    * Converts `axum::Request` into `ProtocolCtx` and then into a `RequestEnvelope` via the `HttpEndpoint` service type.
* `Protocol` enum (`src/models/protocol.rs`) has `Http` plus several other protocols but **no explicit HTTP/3 variant**.
* Config loading/validation (`src/config/config.rs`) already merges `[network.*]` sections and network maps into `Config.network: HashMap<String, NetworkConfig>`.
* Adapter registry integration tests (`tests/adapter_registry_integration.rs`) exercise starting/stopping networks backed by `[network.name.http]` with a single HTTP adapter.
# Design decisions
1. **HTTP/3 as a separate adapter instance, same `Protocol::Http`**
    * We will keep `Protocol::Http` as the required protocol for HTTP and HTTP/3 services to avoid touching service resolution and protocol mapping.
    * `Http3Adapter` will report `Protocol::Http` from `protocol()`, so `AdapterRegistry` does not need to branch on a new `Protocol` variant.
    * The distinction between HTTP/1.x and HTTP/3 remains at the adapter/config level, not in `Protocol`.
2. **Pure-Rust stack: `quinn` + `h3` + `rustls`**
    * Use `quinn` for QUIC over UDP with TLS 1.3 handled by `rustls`.
    * Use `h3` crate with its `quinn` backend for HTTP/3 framing.
    * This avoids BoringSSL/C toolchain requirements.
3. **Config model extension rather than replacement**
    * Extend `NetworkConfig` with an optional `http3: Http3Config` field.
    * `Http3Config` contains:
        * `bind_address: String`
        * `bind_port: u16`
        * `cert_path: String`
        * `key_path: String`
    * The existing `[network.name.http]` block remains unchanged and continues to drive the existing HTTP adapter.
    * New TOML shape example:
```toml
[network.default]
interface = "wg0"
enable_wireguard = false
[network.default.http]
bind_address = "0.0.0.0"
bind_port = 8080
[network.default.http3]
bind_address = "0.0.0.0"
bind_port = 443
cert_path = "/etc/harmony/certs/fullchain.pem"
key_path  = "/etc/harmony/certs/privkey.pem"
```
4. **Initial routing approach**
    * To keep scope manageable, the first iteration will **not** attempt to share Axum's router directly.
    * Instead, HTTP/3 requests will:
        1. Be parsed into method, path, headers, query, body by the HTTP/3 adapter.
        2. Construct a `ProtocolCtx` equivalent to what `HttpAdapter::http_request_to_protocol_ctx` produces (including `meta` entries for `path`, `path_with_query`, `full_path`, `protocol`).
        3. Use the same service + pipeline machinery as the HTTP adapter:
        * Resolve `Endpoint` and `Pipeline` from `Config` based on pipeline membership for the network and service routing (reusing `Endpoint.resolve_service()` and `PipelineExecutor::execute`).
        4. Call `ServiceType::build_protocol_envelope` and `endpoint_outgoing_response` as the HTTP adapter does, so HTTP/3 behaves like HTTP/1.x at the application layer.
    * If the amount of duplicated logic between HTTP and HTTP/3 adapters becomes large, we can refactor shared pieces later into helper functions.
5. **AdapterRegistry behavior**
    * `determine_required_protocols` remains unchanged; it only determines `Protocol::Http` once per network for HTTP-like services.
    * At adapter creation time, when `Protocol::Http` is required:
        * If `NetworkConfig.tcp_config` is present, create an `HttpAdapter` (current behavior).
        * If `NetworkConfig.http3` is present, also create an `Http3Adapter` for that network.
    * This means a network can simultaneously expose HTTP/1.x/2 (via Axum) and HTTP/3 on different ports, sharing pipelines and endpoints.
6. **TLS configuration**
    * HTTP/3 requires TLS 1.3 with ALPN `h3`. We'll implement a helper that:
        * Loads certificate chain and private key from PEM files specified in `Http3Config` via `rustls-pemfile`.
        * Builds a `rustls::ServerConfig` with appropriate cipher suites and ALPN (`["h3"]`).
        * Wraps this in a `quinn::ServerConfig` for use in the HTTP/3 adapter.
    * We will not attempt extremely flexible certificate management in this iteration; we’ll assume a single cert/key pair per network.
7. **Testing strategy**
    * Unit-level tests where possible (e.g., TLS config loader, mapping from HTTP/3 request headers to `ProtocolCtx`).
    * Integration test that:
        * Builds a small config with one network exposing both `[network.test.http]` and `[network.test.http3]` plus a simple endpoint and pipeline (e.g. echo).
        * Starts Harmony via `Config::from_args` and `AdapterRegistry::start_network`.
        * Uses a small in-test HTTP/3 client (quinn + h3 client APIs) to send a single GET/POST request over HTTP/3 to the configured port.
        * Verifies we receive a valid response and that the adapter shuts down cleanly.
    * Tests will be designed to be deterministic and reasonably fast; if the end-to-end HTTP/3 test proves flaky in CI, we can mark it `#[ignore]` with a clear TODO and keep unit tests covering the rest.
# Proposed changes
## 1. Config model updates
**Files:**
* `src/models/network/config.rs`
**Changes:**
* Add `Http3Config` struct and an optional field to `NetworkConfig`:
    * `pub http3: Option<Http3Config>` with `#[serde(default)]`.
    * `Http3Config` derives `Deserialize`, `Clone`, `PartialEq`, `Default`.
* Ensure `Default` impl for `NetworkConfig` still works (likely implicitly via `#[serde(default)]` and derive).
* No changes to existing `TcpConfig` aliasing; `[network.name.http]` remains the primary TCP listener.
**Validation:**
* Extend `Config::validate_networks` to perform basic checks on `Http3Config` if present:
    * `bind_address` not empty;
    * `bind_port != 0`;
    * `cert_path` and `key_path` non-empty.
* Keep validation strict but focused; deeper TLS validation (e.g., existence/readability of files) will be handled at runtime by the adapter with clear error logs.
## 2. Dependencies and Cargo configuration
**File:**
* `Cargo.toml`
**Changes:**
* Add pure-Rust QUIC/HTTP3 + TLS dependencies:
    * `quinn` with `rustls` and `runtime-tokio` features.
    * `h3` with `quinn` backend feature.
    * `rustls` (matching `quinn` version) and `rustls-pemfile` for reading PEM files.
* Ensure there are no conflicting TLS stacks (stay consistent with existing `reqwest` `rustls-tls-webpki-roots` usage).
## 3. New Http3Adapter implementation
**Files:**
* `src/adapters/http3/mod.rs` (new)
* Possibly small helpers in a new `src/adapters/http3/requests.rs` or similar if it helps organization.
**Core responsibilities:**
* Implement `ProtocolAdapter` for `Http3Adapter`:
    * `protocol()` returns `Protocol::Http` (HTTP/3 is just another transport for HTTP services).
    * `from_network(network_name, &NetworkConfig)`:
        * Panic or return error if `network_config.http3` is `None` (this should only be called when config says HTTP is required and `http3` is configured).
        * Parse `bind_address` + `bind_port` into `SocketAddr`.
    * `start(config: Arc<Config>, shutdown: CancellationToken)`:
        * Build `quinn::ServerConfig` from `Http3Config` using TLS helper.
        * Bind a `tokio::net::UdpSocket` to the configured address.
        * Create a `quinn::Endpoint` with the server config.
        * Spawn an async task to:
        * Accept incoming QUIC connections.
        * For each, create an `h3::server::Connection` and serve HTTP/3 requests until connection close or shutdown.
**Request handling pipeline:**
* For each accepted HTTP/3 request stream:
    1. Collect request:
        * Method, path, headers from `h3` request object.
        * Body bytes from DATA frames until end-of-stream.
    2. Build a `ProtocolCtx` similar to `HttpAdapter::http_request_to_protocol_ctx`:
        * `protocol = Protocol::Http`.
        * `payload = body_bytes`.
        * `meta`: `"protocol" = "http3"`, `"path"`, `"path_with_query"`, `"full_path"`.
        * `attrs` JSON object:
        * `method`, `uri`, `headers` (String -> String), `cookies`, `query_params`, `cache_status`.
        * Reuse the same query and cookie parsing logic used by the HTTP adapter where possible (e.g., via shared helpers that operate on method/path/headers strings).
    3. Resolve endpoint + pipeline:
        * Find the pipeline(s) that contain this network (similar to what `Http` router logs/uses).
        * For each endpoint in those pipelines, rely on the service’s `build_router` and/or `path_prefix` semantics to determine if it should handle this path.
        * To keep initial scope manageable and avoid duplicating all router logic, we may:
        * Reuse existing service routing logic (e.g., endpoints’ `build_router` returning `RouteConfig`) by writing a small path-matching helper that uses the generated routes.
    4. Invoke service + pipeline:
        * Call `service.build_protocol_envelope(ctx.clone(), endpoint.options)`.
        * Call `PipelineExecutor::execute(envelope, pipeline, &config, &ctx)`.
        * Call `service.endpoint_outgoing_response(response_envelope, endpoint.options)` to get a `Response<Body>`-like structure or `ResponseEnvelope<Vec<u8>>` (depending on service interface).
    5. Map response back to HTTP/3:
        * Extract status code and headers.
        * Use `h3::server::Connection` APIs to send headers (`:status`, plus normal headers) and body data on the HTTP/3 stream.
**Error handling:**
* Translate pipeline errors to HTTP status codes in the same way as `map_pipeline_error_to_status` in `src/adapters/http/router.rs`.
* Bubble up adapter-level errors to logs; ensure a failing connection does not crash the entire adapter.
## 4. AdapterRegistry integration
**File:**
* `src/adapters/registry.rs`
**Changes:**
* Import the new `Http3Adapter` module.
* In `start_network`:
    * After computing `required_protocols`, when iterating protocols:
        * For `Protocol::Http`, create:
        * One `HttpAdapter` using `NetworkConfig.tcp_config` (as today).
        * If `NetworkConfig.http3.is_some()`, also create an `Http3Adapter` via `Http3Adapter::from_network`.
* Keep the adapter lifecycle (shutdown token, JoinHandle storage) unchanged; multiple adapters for the same network are already supported via the `Vec<AdapterHandle>`.
## 5. Tests
**a. Unit tests for Http3Config and validation**
* **File:** `src/models/network/config.rs`
* Add tests to ensure:
    * `NetworkConfig` deserializes correctly with and without `[network.*.http3]` sections.
    * Invalid configurations (e.g., port 0, empty cert path) are rejected by `validate_networks`.
**b. Unit tests for TLS config loader**
* **File:** `src/adapters/http3/mod.rs` (or a dedicated `tls.rs` submodule).
* Test that given minimal PEM cert+key on disk, the helper returns a valid `quinn::ServerConfig`.
* Use test-only self-signed certs created on the fly or from static test fixtures.
**c. AdapterRegistry integration tests including HTTP/3**
* **File:** `tests/adapter_registry_integration.rs` or a new `tests/http3_adapter_integration.rs`.
* Add scenarios:
    * Config with network that has `[network.test.http]` and `[network.test.http3]` but **no pipelines** referencing that network:
        * Registry logs a warning, but starting network is allowed and does not panic.
    * Config with a simple pipeline using an HTTP endpoint on that network:
        * Registry decides `Protocol::Http` is required.
        * Both HttpAdapter and Http3Adapter are created and started.
        * `get_running_networks` still reports a single network name.
**d. End-to-end HTTP/3 request test**
* **File:** new `tests/http3_e2e.rs`.
* Steps:
    1. Create temporary config directory with:
        * Minimal `proxy`, `logging`, and `storage` sections.
        * One `network.http` (HTTP/1.x) and one `network.http3` listener on different ports.
        * A simple pipeline + endpoint + backend (e.g. echo) bound to that network.
        * Test TLS cert/key files suitable for local `localhost` connections.
    2. Load config via `Config::from_args` and start network via `AdapterRegistry`.
    3. Spin up a small HTTP/3 client using `quinn` + `h3` client APIs to:
        * Connect to the HTTP/3 port.
        * Send a GET or POST request to the echo endpoint.
        * Read the response and assert status and body.
    4. Shut down the network via `AdapterRegistry::stop_network` and ensure no panics.
* If test flakiness appears (e.g., timing-sensitive QUIC handshake), consider marking the e2e test as `#[ignore]` with a TODO and rely on unit/integration tests in the short term.
# Risks and mitigations
1. **QUIC/HTTP3 complexity and flakiness**
    * Mitigation: Start with minimal, well-logged implementation; wrap risky operations with clear `tracing::error!` messages; keep HTTP/3 adapter isolated so failures do not affect HTTP/1.x.
2. **TLS configuration errors**
    * Mitigation: Early, explicit logs if certificate/key loading fails; clearly differentiate config validation errors from runtime TLS errors.
3. **Routing divergence between HTTP/1.x and HTTP/3**
    * Mitigation: Carefully mirror `HttpAdapter::http_request_to_protocol_ctx` semantics and route construction behavior; write tests that hit the same endpoint over HTTP and HTTP/3 and compare behavior.
4. **Dependency compatibility**
    * Mitigation: Choose `quinn`/`h3`/`rustls` versions compatible with current Rust and ecosystem; if needed, gate HTTP/3 under a cargo feature flag so it can be disabled if compatibility issues arise.
# Open questions for review
* Should HTTP/3 be represented as its own `Protocol::Http3` variant in `Protocol`, or is reusing `Protocol::Http` acceptable for now? (Plan currently keeps a single `Http` protocol to minimize changes.)
* Do we want to support **HTTP/3-only** networks (no `[network.name.http]`), or must every HTTP/3 network also expose HTTP/1.x? (Plan assumes HTTP/3 can be configured independently, but sharing networks is recommended.)
* Should HTTP/3 support be behind a Cargo feature flag (e.g., `http3`) for environments where QUIC is not desired or supported?
